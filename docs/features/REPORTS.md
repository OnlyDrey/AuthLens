# Reports

Status: implemented in source (NAV-4); focused backend and browser tests pass; Windows acceptance pending. Navigation and routes:
[navigation](../architecture/NAVIGATION.md#routing-contract).

Reports is a top-level module with four pages, in this order: **Review Reports** (the default), **Access Reports**, **SoD Reports** and
**Evidence**. There is no Reports Overview page. `#/reports` opens the first page the account may use.

## Availability and authorization

`GET /api/reports/availability` returns the report catalogue for the signed-in account: each report with its page, description, formats,
supported review contexts, configurable columns and whether it is available (with the reason when it is not), plus the pages that hold at least
one available report. It is built from the existing permissions (`read` and `export`), the SoD feature switch and the loaded data:

- Reports does not depend on the SoD switch as a module. With SoD turned off, SoD reports are not offered; the Account Review, Position
  Changes and access reports stay available where the data is loaded.
- A report that only lacks data (for example Position Changes without an Employee Directory import) is listed as unavailable with its reason.
- The main navigation shows Reports only when at least one report page is available, and a page the account may not use resolves to an
  authorized one, so there is no empty destination.
- Every report endpoint keeps its own authorization and SoD gating, independent of what the navigation shows. Viewing-role accounts may use the
  reports their permissions allow; centralizing reports grants no access to data that was restricted before.

Each report form shows its description and only the controls the report supports: parameters and filters, the review context where a frozen
period is supported, column selection and delimiter for configurable CSV reports, a preview of the matching rows (count and first ten rows)
and *Generate*. Every report calls the endpoint its source page uses, with the same filter semantics, so counts match the source page. The
contextual exports on the operational pages remain.

## Configurable columns

The configurable CSV reports (Account Review, Position Changes, Compare Users, User Directory, release role list, release assignments) share
one backend writer (`ConfigurableCsv` in `V1Reports.cs`), and the Work Queue export keeps its existing column model:

- Report-specific column definitions with labels, a default selection and required columns (the SAP username, and the identifier where the
  report needs it); a required column cannot be left out, unknown or repeated columns are refused (422).
- Columns are written in the requested order; without a selection the defaults in definition order. Every field is quoted and carries the
  existing spreadsheet-formula guard; files are UTF-8 with BOM; the delimiter is the report's default (comma for Account Review, Position
  Changes and Compare Users, semicolon for the access exports) or the one requested.
- Without report options the access exports return their unchanged v1 files (Python parity), and the moved Account Review and Compare Users
  exports keep the columns and comma format of the earlier browser exports.
- Fixed-layout DOCX and PDF reports and the SoD CSV exports keep their fixed columns.

## Account Review and Compare Users exports (backend)

The Account Review CSV is built from the same server query as the Account Review list (`V1AccountReview.ListRowsAsync`: filters, sort and
completed-review handling across every page). The Compare Users CSV writes one row per assignment interval of each compared role or
transaction, as the browser export did. The pages and Reports use these endpoints; the earlier browser builders are removed.

## Position Changes report

One row per detected position change of the filtered population: SAP username, name, SAP User Group, changed fields, previous and current
department and job title, when the change was first seen in an Employee Directory import (and, optionally, the previous and current import
times), the position change review status and the Account Review decision (state, reviewer, time, rationale). Filters: review status
(pending, reviewed, all), changed field, and the Account Review search and population filters. Only values the directory imports recorded are
exported; the date an organizational change actually took effect is not in the data and is not invented. The Position Changes page has the
same export.

## Evidence

Evidence lists the review periods with their lifecycle state and, for frozen periods (Approved, Closed), the integrity checksum of the frozen
evidence; reports are regenerated from a frozen period in Review Reports. Current report generation, frozen review-period evidence and reports
regenerated from frozen evidence are separate: generated report files are not stored.

## Not included (not implemented)

Historical access reports, stored generated report files or document archives, new access-history snapshots, report retention, scheduling
and automated delivery. Access Reports use the current data snapshot.
